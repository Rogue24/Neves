# 06 When To Use：什么时候该用，什么时候不该用

## 一句话先讲明白

宏不是为了“少写几行代码”，而是为了减少真实复杂度。

如果用了宏以后，团队更难理解、更难调试，那就是用错了。

## 生活类比

宏像洗碗机：

- 每天一堆盘子，流程固定，人工容易烦：值得用。
- 只有一个杯子，非要搬洗碗机：过度设计。

## 该用宏

### 1. 重复样板稳定、机械、容易写错

例如很多类型都要生成同样规则的调试描述、路由表、协议胶水。

### 2. 能把错误提前到编译期

例如 URL、资源名、路由名、配置 key。

### 3. 生成规则清楚

别人看到宏名和输入，就能猜到展开后大概是什么。

### 4. 比普通手段更能降低复杂度

先问自己：

- 函数能不能解决？
- 泛型能不能解决？
- protocol extension 能不能解决？
- property wrapper 能不能解决？

如果这些都表达得很清楚，就先别上宏。

## 不该用宏

### 1. 只是为了少写几行代码

少写不是唯一目标。可读、可调试、可维护更重要。

### 2. 业务规则频繁变化

宏一旦承载频繁变化的业务，会让复杂度藏到编译期插件里。

### 3. 团队大多数人读不懂展开结果

宏会影响团队协作。只有作者懂，不算真的好用。

### 4. 错误信息难懂

如果宏报错比原问题还难懂，调试成本会反超收益。

### 5. 普通 Swift 已经够好

普通函数、泛型、协议扩展、property wrapper 是第一选择。

## 决策口诀

```text
重复到烦、规则稳定、错误能提前，才考虑宏。
看不见的复杂度，不要用宏藏起来。
```

## 最终判断

一个宏值得存在，应该满足：

- 调用端更清楚。
- 错误更早暴露。
- 展开结果可预测。
- 团队维护成本更低。

不满足这些，就别为了用宏而用宏。
